# ตรวจเว็บไซต์เทียบแนวทางของเจ้าของ — 12 พฤศจิกายน 2026

คำถาม: “มีอะไรต้องแก้ไขเว็บไซต์ไหม ตามแนวทางที่ให้ไป”

ข้อสรุป: หลายส่วนตรงแล้ว โดยเฉพาะการระบุว่าเป็น POS ภาพแอปจริง และการแยกราคา
แต่ยังมีข้อมูลสิทธิ์พนักงานที่ไม่ตรงกับโค้ด และงานเส้นทางลูกค้า/ภาพประกอบที่ยังไม่ครบแนวทาง
รอบนี้เป็นการตรวจและบันทึกข้อเสนอ ไม่ได้แก้ไฟล์เว็บไซต์หรือเผยแพร่

## ขอบเขตและหลักฐาน

- แนวทาง: [แกนหลักเว็บไซต์](website-development-core.md) และ [มาตรฐานเนื้อหาจาก PDF](website-content-standard.md)
- เปิดเว็บไซต์จริงผ่าน Chromium/Edge ที่ความกว้าง 390 และ 1440 พิกเซล:
  `/`, `/features/`, `/pricing/`, `/guides/getting-started/`, `/marketplace/`
- ทั้ง 5 หน้าตอบ HTTP 200 และ HTML ตรงกับไฟล์ `public/` ใน working tree ที่สะอาด
  ณ commit `facfe51`; โค้ดเว็บไซต์ล่าสุดรวม `5714a72`
- ตรวจ HTTP `/retail/` และ `/restaurant/`: ทั้งสองตอบ 404 เป็นหน้าที่ยังไม่ได้สร้าง
  ไม่ใช่รายงานว่ามีลิงก์เสียบนเว็บไซต์อยู่แล้ว
- วัดความกว้างเอกสารทั้ง 10 สถานะ ไม่เกิน viewport และไม่พบ JavaScript page error
  ทดสอบสลับประเภทร้านและรอบรายปีในหน้าราคาได้
- ตรวจภาพหน้าแรก มือถือ/เดสก์ท็อป ภาพการ์ดฟังก์ชันและ Footer บนมือถือ
  รวมถึงคู่มือเริ่มต้นและหน้าฟังก์ชัน; เป็นเบราว์เซอร์จำลองขนาดจอ ไม่ใช่มือถือจริง
- หลักฐานในเครื่อง: `D:/pokpok-website-direction-20261112/audit-live.json`,
  HTML ที่ดึงจากเว็บจริง และภาพ `home-390.png`, `home-1440.png`,
  `features-home-390.png`, `features-1440.png`, `footer-390.png`,
  `guides-getting-started-390.png`
- ตัวอ่านเว็บค้นหามีข้อมูลหน้าแรกเก่าที่ไม่แสดงการ์ดฟังก์ชันใหม่ จึงใช้ HTML สดจากเบราว์เซอร์
  ซึ่งตรงกับซอร์สเป็นหลักฐานสถานะปัจจุบัน ไม่ใช้ผลค้นหานั้นสรุปว่าการ์ดยังไม่มี

## สิ่งที่ควรแก้ เรียงลำดับ

### 1. แก้จำนวนบัญชีในแพ็กเกจ Full ให้ตรงระบบ — สำคัญที่สุด

**ปัจจุบัน:** หน้าแรกและหน้าราคาเขียน “รองรับบัญชีผู้ใช้งานสำหรับพนักงาน 3 บัญชี”
ทั้งข้อความ HTML และ `planFeatures` สำหรับร้านค้าปลีก/ร้านอาหาร
หน้าสมัครใช้คำว่า “พนักงาน 3 ผู้ใช้” ด้วย

**หลักฐาน:** `public/index.html:204`, `public/pricing/index.html:60`,
`public/js/site.js:19`, `public/subscribe/index.html:365`.
แต่ `lib/screens/staff_screen.dart:19` ระบุว่าจำนวนรวมเจ้าของ และบรรทัด 89 คำนวณ
`extraAllowed = cap - 1`; Full มี cap 3 ตาม `lib/services/entitlements.dart:18`.
ฝั่ง Functions `functions/staff_access.js:21` คืน staffCap 2 สำหรับ Full
และบรรทัด 89 บังคับจำนวนพนักงานที่เปิดใช้งานตาม cap นี้

**เสนอ:** “รองรับผู้ใช้งานรวม 3 คน (เจ้าของ 1 คน และพนักงาน 2 คน)”
ปรับทั้ง HTML, ข้อความหลังสลับประเภทร้าน และหน้าสมัคร/ต่ออายุ
นี่คือแก้คำอธิบายให้ตรงโค้ด ไม่ใช่เพิ่มสิทธิ์แพ็กเกจโดยอัตโนมัติ
PDF หน้า 9 กำชับให้ยืนยันความหมายของ 3 บัญชีก่อนใช้ จึงควรทำก่อนงานตกแต่ง

### 2. แยกหน้าร้านค้าปลีกและร้านอาหารให้เป็นเส้นทางจริง

**ปัจจุบัน:** แถบประเภทร้านใต้ Hero เป็น `span` ไม่ใช่ลิงก์
(`public/index.html:79`); หน้าฟังก์ชันใช้ปุ่มซ่อน/แสดงเนื้อหาในหน้าเดียว
(`public/features/index.html:18`, `public/js/site.js:10`). ยังไม่มีหน้า Retail/Restaurant

**เสนอ:** สร้างหน้าเฉพาะธุรกิจพร้อมหัวข้อ ปัญหาของร้าน ฟังก์ชัน ภาพจริง แพ็กเกจ และ CTA
แล้วทำทางเข้าจากหน้าแรก/เมนู/หน้าฟังก์ชัน ตรงกับแกนหลักข้อ 3 และข้อ 9
ไม่ต้องรื้อการสลับราคาเดิม แต่ให้ลิงก์จากหน้าเฉพาะธุรกิจพาไปบริบทแพ็กเกจที่ถูกต้อง

### 3. เติมภาพการทำงานให้การ์ดฟังก์ชัน

**ปัจจุบัน:** หน้าแรกมีการ์ดหลัก 4 รายการแล้ว: Sales & Checkout, Inventory,
Tables & Kitchen, Reports พร้อมภาษาไทย ประโยชน์ และแพ็กเกจ
แต่ทั้ง 4 การ์ดมีเพียง SVG icon ไม่มีภาพหน้าจอหรือ Product Mockup ของงานนั้น
หน้าแรกมีภาพแอปใน Hero เพียงภาพเดียว; หน้าฟังก์ชันมีภาพหน้าออเดอร์หนึ่งภาพ

**เสนอ:** ใช้ภาพจริงของหน้าขาย สินค้าคงเหลือ ครัว และรายงานประกอบแต่ละงาน
จัดภาพและคำอธิบายให้สัมพันธ์กัน ตรงแกนหลักข้อ 4 ไม่จำเป็นต้องเพิ่มการ์ดเกิน 4 รายการ
ภาพสต็อก/ครัว/รายงานใหม่ต้องมาจากร้านทดสอบที่อนุญาต ไม่ใช้ภาพหน้าขายแทนทุกฟังก์ชัน

### 4. เก็บคำศัพท์ที่ยังหลุดจากมาตรฐาน และย่อคำอธิบาย Hero

**ปัจจุบัน:** คำหลักใน Hero, แพ็กเกจ และ FAQ ปรับแล้ว แต่ยังมี “สั่งของเข้าร้าน” ในเมนู
“รับเงินสด” และ “ก่อนของขาด” ในการ์ดฟังก์ชัน และ “งานร้าน” ในหัวข้อหน้าฟังก์ชัน
Hero บนมือถือมีคำอธิบายยาวประมาณ 6 บรรทัดก่อนปุ่มหลัก

**เสนอ:** ใช้ “สั่งซื้อสินค้าเข้าร้าน”, “รับชำระด้วยเงินสด”,
“วางแผนสั่งซื้อก่อนสินค้าหมด” ให้ตรงมาตรฐาน และตรวจคำเดียวกันทุกหน้ารวมหน้าสมัคร
Hero เก็บประโยชน์หลักไว้ 2–3 ประโยคสั้น ย้ายรายละเอียดเฉพาะธุรกิจไปหน้าที่เกี่ยวข้อง
H1 ปัจจุบันระบุประเภทผลิตภัณฑ์และกลุ่มลูกค้าชัดอยู่แล้ว ไม่จำเป็นต้องเหมือนตัวอย่าง PDF ทุกคำ

### 5. ทำคู่มือติดตั้งเป็นภาพทีละขั้น

**ปัจจุบัน:** หน้าแรกมีขั้นตอน APK/TestFlight และระบุว่า iOS เป็นรุ่นทดสอบแล้ว
แต่ `/guides/getting-started/` เป็นรายการข้อความ 4 ขั้น ไม่มีภาพในเนื้อหาหลัก
อ้างอิงรุ่น 1.2.71 (88) ขณะที่รุ่น Android ที่บันทึกไว้ใน HANDOFF คือ 1.2.76 (93)

**เสนอ:** ตรวจขั้นตอนกับรุ่นปัจจุบันแล้วเพิ่มภาพติดตั้ง Android และเข้าร่วม TestFlight
พร้อมวิธีเริ่มตั้งค่าร้านและทางติดต่อเมื่อทำต่อไม่ได้
ไม่เปลี่ยนเลขเวอร์ชันบนคู่มือหรือภาพเก่าให้ดูใหม่โดยไม่ได้ตรวจจริง

### 6. เพิ่มลิงก์ช่วยเหลือและเก็บ SEO ให้ครบ

**ปัจจุบัน:** Footer มี 3 กลุ่ม ผลิตภัณฑ์/ติดต่อ/ช่วยเหลือ ซึ่งใกล้ PDF ฉบับใหม่
แต่ส่วนช่วยเหลือมีเฉพาะ Privacy/Terms ไม่มีลิงก์ไป FAQ
หน้าที่ตรวจมี H1, Title, Meta Description และภาพหน้าจอมี Alt Text แล้ว
`public/sitemap.xml` ยังใช้ lastmod 2026-11-05 สำหรับหน้าที่เพิ่งแก้ 11–12 พฤศจิกายน

**เสนอ:** เพิ่ม FAQ และทางติดต่อทีมงานใกล้จุดเลือกแพ็กเกจ/ดาวน์โหลด
ปรับ lastmod ตามการแก้เนื้อหาจริง และเพิ่มหน้าเฉพาะธุรกิจเมื่อสร้างเสร็จ
การเลือก Footer 3 หรือ 4 กลุ่มเป็นความต่างของแนวทางสองชุด ไม่ใช่บั๊กการแสดงผล
ควรรักษาลิงก์ที่ลูกค้าต้องใช้ให้ครบก่อนพิจารณาจำนวนคอลัมน์

## ส่วนที่ตรงแนวทางแล้ว

- Hero บอกว่าเป็นแอป POS สำหรับร้านค้าปลีกและร้านอาหาร มีปุ่มทดลองใช้ชัด
- ใช้สี Burgundy เป็นสีเน้นบนพื้นอ่อน และมีภาพแอปจริง ระบุรุ่น/วันที่/ข้อมูลร้านทดสอบ
- มีฟังก์ชันหลัก 4 รายการ พร้อมชื่อภาษาอังกฤษ คำอธิบายและประโยชน์ภาษาไทย
- หน้าเว็บแยก Features, Pricing, Guides, Marketplace และบทความแล้ว
- ราคาแยกร้านค้าปลีก/ร้านอาหาร มีรายเดือน/รายปี ยอดรายปีและค่าเฉลี่ยแยกกัน
- มีเงื่อนไขทดลองใช้ ข้อมูลค่าใช้จ่ายภายนอก และคำอธิบาย iOS/TestFlight
- FAQ อธิบายข้อมูลที่ซิงก์แล้ว แทนคำรับประกันว่าข้อมูลทุกอย่างไม่มีวันหาย
- ไม่พบการล้นแนวนอนใน 5 หน้าที่ตรวจที่ 390/1440 พิกเซล

## สิ่งที่ยังไม่สรุปจากรอบนี้

ไม่ได้ทดสอบทุกฟีเจอร์หรือสิทธิ์แพ็กเกจบนแอปจริง ไม่ได้ตรวจการจ่ายเงินจริง
ไม่ใช่ผล PageSpeed/Core Web Vitals หรือการตรวจ Accessibility ครบทุกเกณฑ์
คำว่าใช้งานออฟไลน์ได้ “ระยะสั้น” ยังควรอธิบายขอบเขตจากพฤติกรรมที่ทดสอบจริงก่อนขยายคำโฆษณา
การเก็บข้อมูลหลังหมดอายุและค่าธรรมเนียมต้องอ้างอิงนโยบายปัจจุบัน ไม่ใช้ตัวอย่าง PDF แทนข้อยืนยัน

ลำดับทำงานที่เสนอ: ข้อมูลสิทธิ์แพ็กเกจ → คำศัพท์ให้ตรงกัน → หน้าแยกธุรกิจและภาพฟังก์ชัน → คู่มือติดตั้ง → Footer/SEO
